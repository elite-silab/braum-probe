# Braum 小白部署指南

> 目标：只使用 GitHub 和 Cloudflare 网页完成部署。除“把 Agent 安装到 VPS”外，不要求在电脑终端里逐条输入命令。

## 先看懂三个配置位置

| 在哪里填写 | 填什么 | 为什么分开 |
|---|---|---|
| `apps/api/wrangler.toml` | D1/KV ID、网站地址、Agent 下载地址 | 普通配置，可以安全提交到 Git |
| API Worker → 变量和机密 | 密码、JWT 密钥、加密密钥 | 密钥不能放进公开仓库 |
| Web Worker → 构建变量 | `PUBLIC_API_URL` | 告诉网页去哪里访问 API Worker |

本地开发只使用根目录一个 `.env`。项目已经不再要求创建或维护 `.dev.vars`。

## 准备账号

你需要：

- 一个 GitHub 账号；
- 一个 Cloudflare 账号，免费套餐可以开始体验；
- 一台使用 systemd 的 Linux VPS，用来安装 Agent；
- 可选的域名。没有域名也可以先用两个 `workers.dev` 地址。

## 第一步：复制项目到自己的 GitHub

1. 打开本项目的 GitHub 页面。
2. 点击右上角 **Fork**。
3. 保持默认设置，点击 **Create fork**。

后面需要改配置时，都可以直接在 GitHub 网页里点文件右上角的铅笔按钮，不必把仓库下载到电脑。

## 第二步：点一下发布 Agent

1. 打开你 Fork 后的仓库，进入 **Actions**。
2. 如果页面要求启用工作流，点击 **I understand my workflows, go ahead and enable them**。
3. 左侧选择 **Agent Release**。
4. 点击 **Run workflow**，版本号保持 `v0.1.0`，再次点击绿色按钮确认。
5. 等待任务变成绿色。仓库的 **Releases** 页面会出现 Linux amd64 和 arm64 文件。

Agent 需要让 VPS 直接下载，因此 Fork 后的仓库及 Release 必须公开；私有仓库需要另行准备可公开访问的 HTTPS 下载地址。

记下你的 Agent 下载地址，格式如下：

```text
https://github.com/你的GitHub用户名/你的仓库名/releases/latest/download
```

官方仓库默认地址是：

```text
https://github.com/elite-silab/braum-probe/releases/latest/download
```

如果使用 Fork 仓库发布 Agent，请把 `elite-silab` 换成自己的 GitHub 用户名。

这是网页操作，不需要自己编译 Go Agent，也不需要创建 Git 标签。

## 第三步：在 Cloudflare 创建 D1 和 KV

Cloudflare 控制台的菜单名称偶尔会调整；找不到时可使用顶部搜索框搜索 `D1` 或 `KV`。

### 创建 D1

1. 进入 Cloudflare 控制台的 **Storage & Databases（存储和数据库）→ D1**。
2. 点击 **Create database**。
3. 数据库名称填写 `braum-production`。
4. 创建后复制 **Database ID**。

### 创建 KV

1. 进入 **Storage & Databases → KV**。
2. 点击 **Create namespace**。
3. 名称填写 `braum-cache`。
4. 创建后复制命名空间的 **ID**。

## 第四步：直接在 GitHub 编辑普通配置

在 GitHub 打开 `apps/api/wrangler.toml`，点击铅笔按钮，先修改以下三处：

```toml
AGENT_RELEASE_BASE_URL = "https://github.com/elite-silab/braum-probe/releases/latest/download"

database_id = "刚才复制的 D1 Database ID"

id = "刚才复制的 KV Namespace ID"
```

`CORS_ORIGINS` 和 `AGENT_API_URL` 此时可以先不改，因为两个 Worker 的正式地址还没有生成。页面底部点击 **Commit changes** 保存。

项目默认只维护一个正式环境，不需要创建或填写 staging 配置。

## 第五步：连接 GitHub 并部署 API Worker

1. 进入 Cloudflare **Workers & Pages**。
2. 点击 **Create application → Import an existing Git repository**。
3. 授权 GitHub，然后选择刚才 Fork 的仓库。
4. 项目名称填写 `braum-worker`，生产分支选择 `main`。
5. 根目录保持仓库根目录，不要填写 `apps/api`。
6. 构建设置填写：

| 设置 | 值 |
|---|---|
| Build command | `pnpm --filter @braum/shared build` |
| Deploy command | `pnpm --filter @braum/api deploy:full` |
| Node version（若有） | `22.12.0` 或更新的 22.x |

如果当前界面只有一个 Deploy command 输入框，就填写 `pnpm --filter @braum/shared build && pnpm --filter @braum/api deploy:full`。

这些内容只粘贴一次，以后每次在 GitHub 更新项目，Cloudflare 会自动运行迁移并部署。

部署完成后，复制 Worker 地址，例如：

```text
https://braum-worker.你的子域.workers.dev
```

### 在网页里填写生产密钥

进入这个 Worker 的 **Settings（设置）→ Variables and Secrets（变量和机密）**，添加以下四项，并全部选择 **Secret/加密** 类型：

| 名称 | 填写内容 |
|---|---|
| `JWT_SECRET` | 密码管理器生成的 64 位随机字符串 |
| `JWT_REFRESH_SECRET` | 另一个不同的 64 位随机字符串 |
| `ENCRYPTION_KEY` | 再生成一个不同的 64 位随机字符串 |
| `ADMIN_INITIAL_PASSWORD` | 你自己设置的管理后台初始密码 |

不要从 `.env.example` 复制本地示例密钥。保存后重新部署一次 Worker，或等待下一次 GitHub 配置提交触发部署。

## 第六步：连接 GitHub 并部署 Web Worker

1. 再次进入 **Workers & Pages → Create application → Import an existing Git repository**，不要选择 Pages。
2. 仍然选择同一个 GitHub 仓库，项目名称填写 `braum-web`。
3. 根目录保持仓库根目录。
4. 构建设置填写：

| 设置 | 值 |
|---|---|
| Build command | `pnpm --filter @braum/shared build && pnpm --filter @braum/web build` |
| Deploy command | `pnpm --filter @braum/web run deploy:worker` |
| Node version（若有） | `22.12.0` 或更新的 22.x |

5. 在 Web Worker 的构建变量中添加普通变量：

```text
名称：PUBLIC_API_URL
值：第五步复制的 API Worker HTTPS 地址
```

6. 重新部署 Web Worker，复制生成的 `workers.dev` 地址。

## 第七步：补齐两个正式网址

回到 GitHub，再次编辑 `apps/api/wrangler.toml` 的正式环境：

```toml
CORS_ORIGINS = "https://braum-web.your-subdomain.workers.dev"
AGENT_API_URL = "https://braum-worker.your-subdomain.workers.dev"
```

上面的域名只是格式示例，请把它们替换为第五、六步从 Cloudflare 复制的实际地址，不要根据账号名称猜测。绑定了自定义域名时填写自定义 HTTPS 地址；多个网页域名之间用英文逗号分隔。提交后 Cloudflare 会自动重新部署 Worker。

## 第八步：登录后台并安装第一台 VPS

1. 打开第六步复制的 Web Worker 地址，并在末尾加上 `/admin`。
2. 邮箱输入 `admin@braum.local`。
3. 密码输入刚才设置的 `ADMIN_INITIAL_PASSWORD`。
4. 进入「VPS 节点」，只填写一个名称即可创建。
5. 后台会生成一条 15 分钟有效的一次性安装命令。
6. 只在被监控 VPS 上执行这唯一一条命令。
7. 如需网站或 DNS 探测，再到「监控目标」只填写地址并关联节点。

约一分钟后，节点应显示在线，并开始出现 CPU、内存、磁盘、流量和探测数据。

节点 ID、位置、坐标、ISP 与系统信息会自动识别，无需提前查询或手工填写。自动位置不准确时，可在节点的“手动修正位置”中调整。

## 上线检查

- API Worker 的 `/health` 页面能看到 `status: ok`；
- Web Worker 首页可以加载，不出现“网络请求失败”；
- `/admin` 能使用初始密码登录；
- 后台创建节点时可以生成安装命令；
- VPS 安装后一分钟内变为在线；
- GitHub Release 同时存在二进制和 `.sha256` 文件。

## 本地体验（可选）

生产部署不需要 `.env`。只有想在自己电脑上改代码时才需要：

1. 安装 Node.js 22.12+ 和 pnpm；
2. 复制 `.env.example` 为 `.env`，按注释填写本地配置；
3. 在仓库根目录安装依赖并启动开发环境：

```bash
pnpm install
pnpm dev
```

`pnpm dev` 会在启动前自动完成本地数据库迁移。

本地只有一个配置文件 `.env`，无需创建 `.dev.vars`，也无需分别给 API 和 Web 配置相同内容。`.env.example` 只在第一次初始化时复制；已有 `.env` 时不要重复覆盖，以免丢失自己的配置。

## 常见问题

### Worker 部署时提示 D1 ID 无效

检查 `wrangler.toml` 正式环境的 `database_id` 是否完整，不要保留尖括号或空格；确认 D1 与 Worker 位于同一个 Cloudflare 账号。

### 页面打开但没有数据

检查 Web Worker 的 `PUBLIC_API_URL` 是否等于 API Worker 的 HTTPS 地址，再检查 API Worker 的 `CORS_ORIGINS` 是否包含当前 Web Worker 地址。修改构建变量后要重新部署 Web Worker。

### 后台不能生成 Agent 安装命令

检查 `AGENT_API_URL` 和 `AGENT_RELEASE_BASE_URL` 是否为真实 HTTPS 地址，并确认 GitHub 的 Agent Release 工作流已经成功。

### 我还能用命令行部署吗

可以。面向开发者的命令、备份、回滚和故障排查保留在 [部署运维文档](部署运维文档.md) 中，但它们不再是新手首次部署的主流程。
